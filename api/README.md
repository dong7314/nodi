# Nodi API

Nodi 프론트엔드의 로컬 저장 기능을 서버 데이터로 전환하기 위한 Go REST API입니다. 구조화된 데이터는 PostgreSQL에, 이미지와 파일 객체는 private MinIO 버킷에 저장하며 SQLite나 Node.js 런타임은 필요하지 않습니다.

## 기술 구성

- Go 1.24, `net/http`, Chi
- PostgreSQL 16+, pgx 연결 풀과 직접 작성한 SQL
- 내장 SQL 마이그레이션
- HTTP-only 세션 쿠키
- bcrypt 비밀번호 해시, SHA-256 세션·파일 토큰 해시
- private MinIO 버킷과 presigned PUT 업로드. 개발용 로컬 디스크 저장도 선택할 수 있습니다.

## 빠른 실행

Docker가 실행 중이면 아래 명령 하나로 PostgreSQL, MinIO와 API를 시작할 수 있습니다.

```bash
cd api
docker compose up --build
```

상태 확인 주소는 `GET http://localhost:8787/health`입니다. Kubernetes probe는 프로세스 liveness용 `/live`와 PostgreSQL readiness용 `/ready`를 구분해서 사용할 수 있습니다. MinIO 콘솔은 `http://localhost:9001`입니다. 개발 중 Go 서버를 직접 실행하려면 PostgreSQL과 MinIO를 먼저 시작한 뒤 환경 변수를 설정합니다.

PowerShell에서는 다음처럼 실행할 수 있습니다.

```powershell
cd api
$env:DATABASE_URL="postgres://nodi:nodi@localhost:5432/nodi?sslmode=disable"
go run ./cmd/server
```

Go 프로그램은 `.env` 파일을 자동으로 읽지 않습니다. 셸이나 실행 구성에서 `.env.example`의 값을 환경 변수로 전달해야 합니다. `DATABASE_URL`은 필수입니다. `AUTO_MIGRATE=true`이면 시작할 때 아직 적용되지 않은 마이그레이션만 실행합니다.

## 부하를 낮추는 설계

- DB 연결 수는 기본적으로 CPU 수의 2배, 최소 4개·최대 20개이며 운영 환경에서는 `DB_MAX_CONNS`로 더 작게 제한할 수 있습니다.
- `MAX_IN_FLIGHT`를 넘는 요청은 대기열을 무한히 늘리지 않고 즉시 `503`으로 응답합니다.
- IP별 요청 제한은 기본 1분 300회, 초기 burst 120회이며 `RATE_LIMIT_PER_MINUTE`, `RATE_LIMIT_BURST`로 조절할 수 있습니다. Docker Compose 개발 환경은 새로고침과 HMR 요청을 고려해 각각 600회, 240회를 사용합니다. 신뢰하지 않은 `X-Forwarded-For`는 사용하지 않습니다.
- 페이지 목록은 기본적으로 본문 블록을 제외하고 keyset pagination으로 조회합니다. 초기 동기화처럼 왕복 횟수를 줄여야 할 때만 `includeBlocks=true`를 사용합니다.
- 검색은 PostgreSQL `tsvector`와 GIN 인덱스를 사용합니다.
- 첨부파일 업로드와 다운로드는 파일 전체를 메모리에 올리지 않고 스트리밍합니다. 24시간 이상 완료되지 않은 업로드 메타데이터와 객체는 주기적으로 정리합니다.
- 서버 종료 시 새 요청을 중단하고 처리 중인 요청과 DB 연결을 정리합니다.

## 인증 정책

최초 가입자는 PostgreSQL advisory lock으로 단 한 명만 관리자 승인을 받습니다. 이후 가입자는 `pending` 상태가 되고 관리자가 승인하거나 거절합니다. 로그인 성공 시 세션은 `HttpOnly`, `SameSite=Lax` 쿠키로만 전달하며 응답 본문이나 브라우저 저장소에 원본 세션 토큰을 노출하지 않습니다.

## API 범위

모든 일반 성공 응답은 `{ "data": ... }`, 오류는 `{ "error": { "code", "message", "details?" } }` 형태입니다. 첨부파일 presign/complete 응답은 기존 프론트엔드 업로드 계약에 맞게 필드를 최상위에 둡니다.

- 계정: 가입, 로그인·로그아웃, 내 프로필, 비밀번호 변경, 가입 승인, 공유 대상 검색
- 개인 홈: 사용자별 전용 저장, revision 충돌 검사, 서버 수준 비공개 보장
- 페이지: 목록·단건·생성·수정·삭제, 블록 저장, 즐겨찾기, 전체 검색, 공개 페이지
- 폴더: 트리 목록·생성·수정·삭제, 순환 구조 방지
- 공유: 페이지별 보기·편집 권한, 동일 원본 페이지의 WebSocket 실시간 변경 전달
- 댓글: 블록 스레드, 2단계 답글, 해결 상태, 개별 댓글·스레드 삭제 권한
- 받은편지함: 공유·댓글 알림, 읽음 상태, 전체 읽음, 삭제
- 인라인 데이터베이스: 상태 JSON과 revision 충돌 검사
- 워크스페이스: 시작 프리셋 최대 5개, 태그 CRUD
- 사용자 설정: 테마 등 계정별 환경 설정 JSON과 revision
- 첨부파일: MinIO 서명 URL, 크기·MIME 완료 검증, 안정적인 토큰 조회 URL, 삭제

프론트엔드 기능과 API의 상세 대조 결과는 [기능 감사 문서](./docs/frontend-backend-audit.md)에 정리되어 있습니다.

자세한 경로는 [라우터](./internal/api/server.go)를 기준으로 관리합니다.

## 검증

단위 테스트와 정적 검사는 다음과 같이 실행합니다.

```bash
go test ./...
go vet ./...
```

실제 PostgreSQL을 사용하는 회귀 테스트와 Go race detector는 별도 Compose 구성으로 실행할 수 있습니다. 아래 명령은 `api` 디렉터리에서 실행합니다. 개발용 Compose와 프로젝트 이름을 분리하며, 테스트 DB는 포트를 공개하지 않고 임시 메모리 볼륨만 사용합니다.

```bash
docker compose -f compose.test.yaml up --abort-on-container-exit --exit-code-from tests
docker compose -f compose.test.yaml down -v
```

Go와 테스트용 PostgreSQL이 이미 있으면 `TEST_DATABASE_URL`을 지정하고 `go test -race -count=1 ./...`로 실행할 수도 있습니다. 통합 테스트는 각자 임의의 스키마를 만들고 종료 시 제거합니다. 스키마와 `pgcrypto` 확장을 만들 수 있는 테스트용 계정을 사용합니다. `TEST_DATABASE_URL`이 없으면 통합 테스트만 건너뛰며, 앱의 `DATABASE_URL`은 사용하지 않습니다.

검증 범위에는 계정별 기본 프리셋·태그, 초기화 재시도, 동시 생성 시 프리셋 제한, 기존 데이터 마이그레이션, 공개 페이지의 하위 페이지·DB 노출 범위, 동시 페이지 저장, 공유·잠금·WebSocket 권한, 페이지 이동·휴지통·복원, 댓글·DB 보존, 로컬 첨부파일 공개 전환과 삭제가 포함됩니다. MinIO의 실제 객체 업로드는 이 테스트 구성에 포함하지 않습니다. 별도 `compose.e2e.yaml`로 실행하는 실제 브라우저·MinIO 검증은 [UI README](../ui/README.md)를 참고합니다.

## 백엔드 보완 사항 (2026-10-02)

- `004_user_scoped_presets_tags.sql`은 프리셋·태그의 기본 키를 `(owner_id, id)`로 변경합니다. 기존 ID와 데이터는 보존하며, 여러 계정이 `daily`, `personal` 같은 기본 ID를 각각 사용할 수 있습니다. `AUTO_MIGRATE=true`로 새 API를 시작하면 적용됩니다.
- 같은 계정·ID로 프리셋이나 태그를 다시 생성하면 기존 값을 `200`으로 반환합니다. 새 생성은 계속 `201`이며, 재시도가 사용자 편집 값을 덮어쓰지 않습니다. 프리셋 5개 제한은 동시 생성 요청에도 적용됩니다.
- 공개 페이지는 본문에서 참조한 인라인 DB만 반환하고 DB 휴지통을 빈 배열로 전달합니다. 공개되지 않았거나 보관된 하위 페이지 참조는 제목을 `비공개 페이지`로 바꾸고 대상 ID를 비웁니다. 원본 데이터와 인증된 사용자 조회는 유지됩니다.
- 페이지 PATCH와 블록 PUT은 현재 상태를 읽는 시점부터 저장까지 행 잠금을 유지합니다. 동시 요청에서 생략한 필드가 이전 값으로 되돌아가는 문제를 방지하며, 기존 revision 충돌 응답과 revision 생략 요청을 지원합니다. 같은 필드를 revision 없이 동시에 수정하면 마지막 저장이 적용되는 정책은 유지됩니다.

Docker Compose는 개발 기본값을 사용합니다. 운영에서는 반드시 DB 비밀번호, `DATABASE_URL`, `PUBLIC_BASE_URL`, `CORS_ORIGINS`, 볼륨 백업 정책을 별도로 설정하고 TLS를 적용해야 합니다.

### 추가 동시성·세션 회귀 검증

- 로그아웃은 해당 세션의 WebSocket을 닫고, 비밀번호 변경과 계정 거절은 해당 사용자의 모든 연결을 닫습니다. 만료 시 연결을 종료하며, 수신 및 브로드캐스트 전에도 세션을 확인합니다. 블록 저장은 세션 잠금을 같은 트랜잭션에서 유지하고 만료 시각을 저장 제한 시간으로 사용합니다.
- 실시간 `page.blocks.patch`에 선택적으로 `mutationId`(최대 128바이트)를 보낼 수 있습니다. 서버는 `page.updated`와 해당 변경의 `page.error`에 식별자를 돌려줍니다. 같은 계정의 여러 탭에서도 자신의 저장 응답을 구별할 수 있으며, 필드가 없는 기존 요청도 지원합니다.
- 폴더 생성·수정·삭제는 계정별로 직렬화합니다. 이동 전 최신 부모 트리와 하위 트리 높이를 함께 검사해 순환과 3단계 초과를 막습니다. PATCH에서 생략한 필드는 최신 값을 보존합니다. 오래된 전체 폴더 상태를 보내지 않도록 클라이언트도 변경 필드만 보내야 합니다.
- 알림 페이지네이션은 결과 연결을 반환한 뒤 읽지 않은 수를 조회하고, 댓글 삭제는 기존 트랜잭션으로 권한을 검사합니다. DB 연결이 한 개뿐인 구성에서도 두 경로를 검증합니다.
- 500자 페이지 제목의 공유, 알림 제목 길이 제한, 비밀번호의 UTF-8 바이트 경계를 검증합니다. 비밀번호는 bcrypt 한도에 맞춰 8~72바이트를 지원하며, 초과 입력은 서버 오류 없이 거절합니다.
- 로그인은 사용자 행 잠금을 유지한 트랜잭션 안에서 비밀번호 확인과 세션 발급을 처리합니다. 비밀번호 변경이 완료되면 먼저 시작한 로그인에서 발급한 세션도 폐기되며, 변경 뒤 잠금을 얻은 로그인은 최신 비밀번호와 승인 상태를 검사합니다. 동시에 들어온 비밀번호 변경도 잠금 안에서 현재 비밀번호를 다시 확인합니다.
- 공유 해제·보기 권한으로 변경과 페이지 저장은 같은 페이지 행 잠금을 사용합니다. WebSocket 블록 변경, HTTP 페이지 PATCH, 블록 PUT은 잠금을 얻은 뒤 별도 쿼리로 최신 권한을 확인합니다. 먼저 승인된 저장이 있으면 공유 변경이 그 저장의 완료를 기다리고, 공유 변경 뒤 실행되는 저장은 거절합니다. 잠금은 필요한 사용자·세션을 먼저, 페이지를 나중에 잡으며 공유 알림의 외래키 검사도 이 순서를 따릅니다.
- WebSocket은 연결 등록 후 최신 snapshot을 읽고, 모든 데이터 송신에서 세션과 페이지 접근 권한을 다시 검사합니다. 읽기 잠금은 최대 5초의 송신 제한 시간 안에서 전송 완료까지 유지하므로 다른 API 인스턴스의 공유 해제와도 순서가 보장됩니다. 접근 해제·페이지 보관·삭제 알림은 본문 없이 종료 신호만 전달합니다.
- 인라인 DB 생성·수정·이동·삭제도 같은 페이지 권한 잠금에 참여합니다. DB ID별로 쓰기를 직렬화한 뒤 원본과 대상 페이지 소유자, 정렬된 페이지를 잠그고 최신 편집 권한과 페이지 잠금을 확인합니다. 페이지 영구삭제는 소유자 잠금을 먼저 잡아 부모 삭제의 외래키 갱신과 DB 이동 사이의 교착을 방지합니다. 트랜잭션을 끝낸 뒤 브로드캐스트하므로 풀 연결이 한 개여도 처리할 수 있습니다.

추가 통합 테스트는 세션 종료·비밀번호 변경·계정 거절·자연 만료·다른 서버에서의 세션 폐기, 만료 전에 시작했지만 페이지 잠금에서 대기한 저장, 같은 계정의 복수 세션, 변경 식별자 응답, 폴더 동시 변경·이동·기존 순환 구조의 복구를 포함합니다.

권한 경합 테스트는 PostgreSQL 트리거와 advisory lock으로 세션 발급·비밀번호 변경·공유 변경·페이지 저장을 정확한 순서로 대기시킵니다. 지연된 이전 비밀번호 로그인, 계정 거절 중 로그인, 중복 비밀번호 변경, 실제 WebSocket 및 HTTP 두 저장 경로의 공유 해제·권한 축소, 사용자/페이지 잠금 순서를 검증합니다.

공유 생명주기 테스트는 HTTP upgrade 중 공유 해제, 다른 API 인스턴스의 공유 해제, 연결 중 변경된 snapshot·권한, DB 쓰기와 공유 해제의 양쪽 실행 순서, DB 이동 후 권한 재검사, 부모 페이지 영구삭제와 자식 페이지로의 DB 이동, 단일 풀 연결의 DB 저장 및 실시간 송신을 검증합니다.


### 첨부 복사·페이지 구조·업로드 완료 보완

- `005_attachment_references.sql`은 페이지·홈·프리셋·인라인 DB의 승인된 첨부 연결과 객체 삭제 대기열을 추가합니다. 배포 전에 마이그레이션을 적용해야 하며, `AUTO_MIGRATE=true`에서는 API 시작 시 적용됩니다. 기존 문서의 실제 파일·이미지·영상·오디오 `props.url` 중 유효한 asset token과 현재 원본 읽기 권한이 있는 연결만 보완합니다. 권한을 확인할 수 없는 과거 URL로 새 접근 권한을 만들지 않습니다.
- 페이지를 복사하거나 첨부 블록을 붙여넣으면 저장 트랜잭션에서 원본 읽기 권한과 토큰을 확인합니다. 복사본은 대상 문서의 현재 공개·공유·보관 상태에 따라 조회되며, 원본 페이지를 영구 삭제해도 유지됩니다. 일반 텍스트 URL과 외부 호스트의 URL은 첨부 연결로 해석하지 않고, 이미 깨진 같은 첨부 URL은 다른 내용 편집을 막지 않습니다.
- 승인된 첨부 연결은 실행 취소를 위해 블록 제거 후에도 리소스 삭제까지 보존합니다. 마지막 참조 리소스와 원본 연결이 모두 사라지면 객체 정리를 예약합니다. 메타데이터 트랜잭션이 실패하면 파일은 유지되고, 커밋 후 객체 저장소 오류는 성공 응답·삭제 알림을 바꾸지 않습니다. 정리 대기열은 서버 시작·presign 정리·다음 삭제 요청에서 재시도합니다.
- 페이지 생성과 구조 변경은 소유자 잠금을 먼저 얻어 서로 다른 페이지를 동시에 상호 부모로 지정할 수 없게 합니다. 재귀 검사는 기존 순환 데이터에서도 종료되며, 부모를 해제해 복구할 수 있습니다. 일반 페이지 쓰기는 소유자 → 페이지 → 정렬된 첨부 순서로 잠가 영구 삭제 및 복사와 순서를 맞춥니다.
- 로컬 업로드는 먼저 임시 파일을 작성하고 완료 행 잠금을 얻은 요청만 최종 파일로 게시합니다. 중복 완료는 기존 파일을 보존한 채 409를 반환합니다. 24시간 지난 미완료 업로드 정리도 같은 행 잠금을 사용하고 진행 중인 완료 요청은 건너뜁니다.

### 하위 페이지의 회원 공유 상속 (2026-10-03)

- `006_inherited_page_shares.sql`의 `effective_page_shares(page_id)`는 현재 페이지부터 동일 소유자의 조상 페이지까지 회원 공유를 조회합니다. 기존 하위 페이지와 새 하위 페이지 모두 적용되며 공유 행을 복사하지 않습니다. 배포 전에 마이그레이션을 적용해야 하고, `AUTO_MIGRATE=true`에서는 API 시작 시 적용됩니다.
- 보기·편집 권한 중 편집 권한이 우선합니다. 하위 페이지에 직접 부여한 권한은 상위 공유를 해제해도 남습니다. 이동·보관·삭제 후에는 현재 트리로 재평가하며, 보관된 조상·소유자가 다른 경계·순환은 통과하지 않습니다. 로그인 없이 사용하는 공개 링크는 기존 페이지별 공개 설정을 따릅니다.
- 공유 편집자는 편집 가능한 부모 아래에 페이지를 생성할 수 있습니다. 생성된 페이지는 부모 소유자에게 속하며 생성자는 상속된 편집 권한을 받습니다. 보기 전용·잠긴 부모에서는 생성할 수 없고, 공유 편집자가 소유자 전용 공개·잠금·보관 설정을 지정할 수 없습니다.
- 페이지·검색·공유 목록, 댓글과 알림, 인라인 DB, 첨부파일, WebSocket이 같은 유효 권한을 사용합니다. 공유 목록의 회원은 선택적으로 `inheritedFromPageId`, `inheritedFromTitle`, `directPermission`을 포함합니다.
- 공유 변경은 소유자 범위의 배타적 advisory lock을, 데이터 쓰기와 실시간 송신은 같은 범위의 공유 잠금을 사용합니다. 사용자/FK → ACL → 페이지 순서로 잠그며, 조상 공유 해제와 대기 중인 하위 페이지 저장·송신을 직렬화합니다. 구조 변경은 기존 소유자 행 잠금으로 보호하고, 커밋 후 하위 페이지의 열린 실시간 연결도 권한을 재평가합니다.

`inherited_sharing_integration_test.go`는 다단계 상속, 직접 공유와의 조합, 생성·검색·댓글·DB·첨부 접근, 이동·보관·삭제, 공유 해제 및 권한 축소와 동시에 대기한 HTTP/DB/생성/WebSocket 저장, 다른 API 인스턴스의 공유 해제와 송신 중인 하위 페이지 프레임을 검증합니다.

### MinIO 완료·정리 경합 보완 (2026-10-04)

MinIO 객체 확인과 완료 표시 사이에 오래된 업로드 정리가 실행되면, 첨부 행과 객체가 삭제된 뒤에도 완료 API가 `uploaded: true`를 반환할 수 있었습니다. 완료 API는 첨부 행 잠금을 얻은 트랜잭션에서 객체를 확인하고 완료를 기록합니다. 완료 처리가 먼저 시작되면 정리는 해당 행을 건너뛰고, 정리가 먼저 완료됐다면 완료 요청은 404로 종료합니다. `minio_completion_integration_test.go`는 실제 PostgreSQL과 지연된 S3 호환 응답을 사용해 두 실행 순서를 재현하며, 수정 전 두 경우 모두 실패한 것을 확인했습니다.

두 경합 검사는 수정 후 각각 10회 반복 통과했습니다. 최종 소스에서 전체 `go test -race -count=1 ./...`, `go vet ./...`와 실제 API·PostgreSQL·MinIO를 사용하는 세 브라우저 통합 검사 30개가 통과했습니다.
